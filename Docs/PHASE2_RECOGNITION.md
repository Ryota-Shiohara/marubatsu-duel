# Phase 2: 手書き認識と紙面入力

ユーザーの無料構成を希望する回答に基づき、まずC#のみで実装する。有償のOpenCV for Unity、OpenCvSharp、外部Pythonプロセス、独自ネイティブDLLは追加しない。Unity/Vuforiaのバージョンは維持する。

## 試し方

1. 既存の `Phase1_BoardTracking` を開き、再生する。シーンを作り直す必要はない。
2. 盤面全体をカメラへ映す。Gameビューの左上にPhase 2パネルが出る。
3. 黄色い枠が中央マスの内側に合うこと、`Rectified cell` に中央マスだけが正面へ補正されて表示されることを確認する。仮の立方体はCPU画像へ描き込まれない。
4. 空欄で `Empty`、中央に黒い○を書いて `Circle`、別の空の用紙の中央に×を書いて `Cross` になるか確認する。右側は二値画像、`stable` は6フレーム以上かつ0.6秒以上継続した診断結果。デバッグ用でゲームの手として確定しない。
5. 紙を回転・傾斜させ、切り出しが同じマスに対応するか確認する。中央が小さすぎる場合はカメラを近づける。手やペンを離してから静止する。
6. 盤面を見失うと切り出し表示と安定化結果が消えることを確認する。空欄に戻すには消すか用紙を交換する。

切り出し対象の変更は再生中のHierarchyに生成される `MarubatsuBoard_v1` の `BoardImageExtractor > Cell Index`（0～8、中央4）で行える。これは画像診断の設定で、ゲームの入力UIではない。再生終了時に初期設定へ戻る。

## 構成

- `CameraFrameProvider`: Vuforiaのフォーマット登録を一元管理し、8 Hzで管理バッファへコピー。行strideを除去し、RGB888フォールバック時はグレースケール変換。フレームの解像度・連番・状態取得時刻・内部パラメーター・カメラ姿勢を同時に渡す。借用バッファはイベント内でのみ有効。
- `CameraFrameProbe`: 同じProviderの最初のフレームだけログに記録。独立したカメラ取得やフォーマット登録は行わない。
- `BoardImageExtractor`: TRACKED時のみ、ターゲット上のセル四隅をカメラ座標へ変換。内部パラメーターを取得画像解像度に合わせてスケールし、生画像座標へ投影する。罫線を避けてセル各辺から6%を除く。初期の12%では通常サイズの○まで端で切れる実例を確認したため、切り出し範囲を広げた。
- `PerspectiveCellSampler`: 正面の単位正方形から生画像四角形へのホモグラフィで逆写像し、双線形補間して96 × 96ピクセルを作る。C#のみ。
- `CellImageProcessing`: Otsu二値化、黒画素率、最大連結成分、閉領域、対角線方向の4腕からEmpty/Circle/Cross/Unknownを推定。信頼度の数値はルールの目安で、統計的に校正された確率ではない。
- `CellDetectionStabilizer`: 別連番の6フレームと0.6秒の一致を要求する。Unknown・低信頼度・0.4秒超の途切れ・追跡ロストで履歴をリセットする。

## 座標変換の根拠・制限

11.4.4の公開API定義とローカルDLLの実装を確認した。Editorの `ConvertScreenToImageSpace` は `Camera.ScreenToViewportPoint` の結果を返す分岐を持つため、画像ピクセル座標として直接使用しない。今回の方式は `CameraDevice.GetCameraIntrinsics()` の `Size`、`FocalLength`、`PrincipalPoint` を利用する。

Unityカメラのローカルは+Z前方・+Y上、画像は左上原点・+Y下として、`u=fx*X/Z+cx`, `v=cy-fy*Y/Z` で投影する。焦点距離と主点は内部パラメーターの基準解像度から画像の有効幅高へ換算する。GUIへの表示時だけTexture2Dの下原点へ変換する。

根拠: [Vuforia Intrinsics公式API](https://developer.vuforia.com/references/unity/classVuforia_1_1Intrinsics.html)、[CameraDevice公式API](https://developer.vuforia.com/references/unity/classVuforia_1_1CameraDevice.html)。

初期実装は `MODE_LINEAR` のカメラのみを扱う。非線形歪みのカメラは未対応として停止する。画像領域外・カメラ後方・退化した四角形・最短辺16ピクセル未満でも停止する。実機のミラー／原点／投影が合うかは切り出し画像で確認が必要。状態取得時刻は撮影時刻の厳密な同期を保証しないため、動かしながら筆跡を確定する用途にはまだ使用しない。

## 確認項目

2026-11-02: PowerShellで合成画像等の21チェックが成功。Unity 6000.3.24f1でコンパイルに成功し、再生時の診断パネル表示と640 × 480のCPUフレーム取得、線形カメラとしての判定を確認した。カメラが盤面を向いていない状態では `Board not tracked` となり、分類を停止することを確認。実際の中央マスの切り出し位置と実筆跡の分類は、次のユーザー確認が必要。

その後のユーザー確認: 中央マスの切り出しは一致し、真上からの分類はある程度動作するとの報告。斜めからも切り出し位置は合うが、分類がUnknownになる。次の画像認識担当の作業は、斜視時の二値画像の線の欠け・太さと分類条件の調整。認識精度の定量評価はまだ行っていない。

斜視対策の追加: セル外縁の紙色から緩やかな明るさの平面を推定して補正し、3×3のクロージングで小さな線切れを補う。×は交点位置と二本の対角線の傾きを一定範囲で探索する。薄い筆跡を拾うためコントラストと二値化の上限も調整し、紙のノイズを空欄とする検証を追加した。単線・＋・大きく離れた筆跡や遮蔽をUnknownのまま保つテストを含め、合成画像等の40チェックが成功。診断パネルの下段にはUnknownの理由も表示する。`Ink touches crop edge` は筆跡が切り出しの端に触れている状態、`Several disconnected strokes` は線が離れている状態、`No loop or four diagonal arms` は○・×の形状条件に合わない状態を示す。実カメラ画像で前者の端切れを確認し、切り出し余白を調整した。全角度・複数筆跡での改善効果は未検証。

## ゲームとの接続

`BoardImageExtractor` は各フレームで9マスを個別に評価し、安定した状態を `PaperMoveInput` へ渡す。F1の診断画面は `CellIndex` で選んだ1マス（初期値は中央）の切り出しと二値画像を表示するためのもので、ゲーム入力を手動で選ぶUIではない。

対局開始時とリセット後は、9マスすべてが空欄と安定して確認されるまで着手を受け付けない。その後は、既に受理した盤面と一致し、手番どおりの新しい記号が1つだけ見つかった場合に着手を試みる。`Unknown`、手番違い、複数の新しい記号、受理済みマスとの不一致は着手にせず、診断状態として保持する。ゲーム側は空欄・手番・対局中かどうかを再確認し、盤面・次の手番・勝敗を表示側へ通知する。

9マスは印刷物を正面から見て左上から横順に0～8。`CellMark` は `Unknown` と `Empty` を含む認識候補の型で、ゲームの確定状態とは別に扱う。

`Tools/Test-Recognition.ps1` をPowerShellで実行すると、Unityを起動せずに分類・安定化・射影補正・ゲーム入力を検証できる。これは合成画像とカメラなしのロジック確認であり、実際の筆跡や実機上の認識精度を保証しない。

コード上は9マスの個別認識を紙面入力へつなぎ、手番・勝敗に反映する。合成画像とカメラなしのチェックもある。一方、実筆跡の精度、照明変化、筆記中や手による遮蔽への十分な耐性は未確認。特に閉じた四角や別の閉曲線も○候補になる可能性があり、○と×以外を十分に除外できるとは扱わない。認識の調整は実機の切り出し位置を確認してから、実筆跡の閾値・形状特徴を見直す。
